2. MASTER DEFECT RULE
Do not treat the visible error as automatically being the root cause.
VISIBLE ERROR
≠
ROOT CAUSE

The root cause must be identified through the documented system flow.

3. ID-ORIENTED DEFECT RULE

↓

↓

↓

↓

The investigation follows the system ID and its rules, not assumptions about a particular person.

28. DEFECT PRIORITY
P0 — CRITICAL
System-wide failure
Security breach
Financial integrity failure
Irrecoverable data corruption

P1 — HIGH
Critical business flow failure
Authorization failure
Major transaction failure

P2 — MEDIUM
Non-critical functional failure
Recoverable integration issue

P3 — LOW
Minor defect
Non-critical presentation / operational issue


29. ROOT CAUSE CONFIRMATION
A root cause is confirmed only when:
CAUSE IDENTIFIED
+
CAUSE REPRODUCED
+
CORRECTION REMOVES FAILURE
+
ORIGINAL TEST PASSES
+
REGRESSION PASSES
